---
title: Running Gazebo
description: How to build and launch robot simulations with the Gazebo sim CLI.
---

Gazebo simulations are launched through the `sim gazebo` CLI:

```bash
sim gazebo <robot_name>
```

<Callout>With **pixi**, prefix it all of the `sim ...` commands here with `pixi run`</Callout>

## Flags

| Option                               | Default | Description                                                          |
| ------------------------------------ | ------- | -------------------------------------------------------------------- |
| `--no-build`                         | off     | Skip the `colcon build` step.                                        |
| `--build-only`                       | off     | Build the workspace but don't launch the simulation.                 |
| `-c`, `--controller-ui`              | off     | Open a keyboard-to-gamepad GUI alongside the simulation (see below). |
| `--ttt` / `--no-ttt`                 | off     | Spawn the TTT task model. Viator only.                               |
| `--follow-rover` / `--no-follow-rover` | on      | Make the Gazebo camera follow Viator. Viator only.                   |
| `--joint-gui` / `--no-joint-gui`     | off     | Open the arm joint control GUI. Viator and arm only.                 |

Available simulation targets include `viator`, `viator_chassis`, and `arm`. Use `viator` for the complete rover with its arm, ZED camera, and GNSS. The component targets are for focused mechanical testing.

The Viator flags can be combined in one command. For example, this starts the controller UI and
TTT model while leaving camera follow at its default:

```bash
sim gazebo viator --controller-ui --ttt
```

Any trailing `name:=value` pairs are passed to ROS launch. The lower-level equivalents
`ttt:=true` and `follow_rover:=false` remain available, along with sensor settings such as
`zed_frame_rate:=30`.

## Driving without a physical gamepad

```bash
sim gazebo viator --controller-ui
```

Opens a small window that, while focused, turns your keyboard into a virtual Xbox 360 gamepad
using Linux's `uinput`. It spoofs a real pad's vendor/product ID and raw axis/button layout, so
anything that reads a gamepad the normal way - like mission-control's browser Gamepad API - sees
it as a connected controller rather than requiring the real hardware. The window includes a live
visualizer of the sticks, triggers and buttons so you can confirm input is flowing before touching
mission-control. Losing window focus immediately releases all input, so it won't leave the rover
driving if you click away.

| Keys         | Virtual pad input       | What mission-control does with it     |
| ------------ | ----------------------- | ------------------------------------- |
| `A` / `D`    | left stick horizontal   | baseplate left / right in arm mode    |
| `W` / `S`    | left stick vertical     | left wheels / shoulder up / down      |
| left / right | right stick horizontal  | wrist left / right in arm mode        |
| up / down    | right stick vertical    | right wheels / elbow up / down        |
| `Z` / `C`    | left / right trigger    | wrist down / up                       |
| `Q` / `E`    | left / right bumper     | claw close / open                     |
| `Space`      | Y                       | double-tap to swap drivebase/arm mode |

This needs `/dev/uinput`, which the Dev Container bind-mounts from the host alongside
`/dev/input` - see [Docker setup](../../setup/docker/) if it's missing or inaccessible.

Any `name:=value` arguments are passed through to the robot's ROS launch file, e.g. `sim gazebo chassis rviz:=false`.

## Cleaning the workspace

To remove build artifacts and do a clean rebuild:

```bash
sim gazebo clean
```

This deletes the ROS build, install, and log directories under `gazebo/.artifacts/`. It keeps ArduPilot's EEPROM, terrain cache, logs, and crash dumps in `gazebo/.artifacts/drone/` so a ROS rebuild does not reset the drone.

## Troubleshooting

<Accordions>
    <Accordion title="Build fails with cryptic errors">
        Run `sim gazebo clean` to delete stale build artifacts, then try again. Stale artifacts
        are the most common cause of unexplained build failures.
    </Accordion>
    <Accordion title="Gazebo window doesn't appear (Dev Container)">
        Connect via your VNC viewer at `localhost:5900` and verify it works with `xeyes`. If the
        display isn't running, restart it with `.devcontainer/x_server.sh`.
    </Accordion>
    <Accordion title='RViz crashes with "Unable to create the rendering window", or Gazebo shows a blank window (macOS/Windows)'>
        The `VirtualGL` path that gives OGRE2 a working GL context isn't active. Check for a
        warning from `sim gazebo` at startup, then see [Docker setup](../../setup/docker/) for
        how to verify and fix it.
    </Accordion>
    <Accordion title="Package not found errors after launch">
        Try running `sim gazebo clean` and building again.
    </Accordion>
    <Accordion title="`sim gazebo ... -c` fails with a /dev/uinput error">
        The error message tells you which fix applies: load the kernel module with
        `sudo modprobe uinput` if it's missing entirely, or add yourself to the `input` group
        (and re-login) if it exists but you can't write to it. Restart the Dev Container
        afterwards so the `/dev/uinput` bind mount picks it up.
    </Accordion>
    <Accordion title="The requested target is not found">
        `sim gazebo <robot_name>` takes a target name (`viator`, `viator_chassis`, `arm` ...)
        from `robots.json`, not a package name. Check the registry or [create a new robot](./adding-robots.mdx).
    </Accordion>
</Accordions>
